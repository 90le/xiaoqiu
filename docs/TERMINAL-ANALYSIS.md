# 终端框架与项目设计分析（用户反馈驱动）

> 2026-09-14 · 起因：用户实测反馈——①悬浮球拖动受限 ②终端交互性差"不是我们之前的终端" ③多标签管理弱
> 结论先行：**架构保留 OpenMinis 分层，交互层按 v1 完全体重做，分三层推进**

---

## 一、用户反馈定性与根因

| 反馈 | 根因 | 定性 |
|---|---|---|
| 悬浮球只能拖左侧 1/3 | **dp 当 px 用**：位置值存的是 dp（0~393），offset 却按像素（屏宽 1080px）解释 → 393/1080≈1/3 | 单位 bug，已修（全 px 化） |
| 终端交互差、不像 v1 | v2 终端 = OpenMinis 自研 emulator + 原生 View，交互只做了「能用」（手动拖滚动/基础长按选择），**v1 打磨的全套手势体系没搬** | 缺的不是框架是交互层 |
| 多标签管理弱 | 已有 ☰抽屉+标签条，但**无常驻感、无命令面板、无 AI 终端区**，且 TabsBar 视觉存在感低 | 功能补齐问题 |

**关键判断**：用户问"应该不是我们之前的终端吧"——对。v1 是 xterm.js（浏览器级终端仿真，10年打磨的交互），v2 是 OpenMinis 自研 Kotlin emulator（ANSI 渲染正确但交互原始）。**换回 xterm.js 是错误方向**（引入 WebView 违背原生架构，v1 的坑重踩），正确方向是**保留 emulator 核心 + 用 v1 的交互设计重做交互层**。

---

## 二、终端栈对比

| 层 | v1（xterm.js） | v2 现状（OpenMinis） | 差距 |
|---|---|---|---|
| 仿真核心 | xterm.js headless + PTY | TerminalEmulator.kt（ANSI/OSC/1537 完整） | ✅ 无差距（1537 是 v2 独有） |
| 渲染 | DOM canvas（浏览器合成） | TerminalNativeView（自绘 canvas） | ✅ 相当 |
| **滚动** | **惯性甩动+边缘滚动+↓回底** | 手动拖拽，无 fling | ❌ 差距最大 |
| **选区** | **自绘像素↔单元格+双拖柄+边缘自动滚** | 系统长按选择（基础版） | ❌ 无拖柄/无边缘滚 |
| 粘贴 | JsBridge 剪贴板原生通道 | 无入口 | ❌ |
| 快捷键 | v7 两行+展开+粘滞 | ✅ 已移植 | ✅ 追平 |
| 悬浮 D-pad | v3 球态/展开/位置记忆 | ✅ 已移植（单位 bug 已修） | ✅ 追平 |
| 多标签 | 会话池+长按重命名+AI区 | 标签条+☰抽屉（已补） | ⚠️ 缺 ⌘面板/AI区 |
| IME | 组合重发+宽度错位双修 | TerminalInputView（有基础处理） | ⚠️ 待实测 |
| 命令面板 ⌘ | commands.json 任务复用 | 无 | ❌ |

## 三、优化方案（三层推进）

### L1 快修层（本轮已做，0.5 天）
- ✅ Dpad 单位修复（dp→px）
- ✅ ☰ 会话管理抽屉
- ✅ 键帽 v1 样式
- 待装机验证

### L2 交互对齐层（v1 手势体系移植，2-3 天）——**核心战役**
| 任务 | v1 参照 | 实现方案 |
|---|---|---|
| 惯性滚动 | 甩动 fling | TerminalNativeView 接 OverScroller（手势抬起→fling 滚 scrollOffset） |
| ↓ 回底按钮 | 滚离底部出现浮动↓ | scrollOffset>0 时右下角浮动钮，点击归零 |
| 粘贴键 | 键盘条粘贴入口 | 键盘条加 📋 键：ClipboardManager→sendText（分块） |
| 选区双拖柄 | 自绘 overlay+两拖柄 | 在 NativeView 上层加 Compose overlay：起点/终点柄，拖动更新选择，边缘自动滚 |
| 边缘自动滚 | 拖柄到边缘时滚动 | 拖柄手势中检测 y 位置→定时滚 |

### L3 架构增强层（1 周内，与战役 C 融合）
| 任务 | 说明 |
|---|---|
| ⌘ 命令面板 | v1 commands.json：保存常用命令（名称+命令+cwd），一键在新标签跑；编辑/删除/二次确认删 |
| AI 终端区 | ChatScreen 的 shell_execute 输出→终端标签（🤖分隔区），Agent 跑的命令实时可见可接管 |
| 标签常驻 | 终端会话在 App 内常驻（已实现 Manager 层）+ 通知栏常驻服务提示（AgentForegroundService 融合） |

### 守住不动的（OpenMinis 好设计）
- emulator/view/session/manager 四层分离
- OSC 1537 URL broker（chat↔终端互通）
- PersistentShell（Agent 长连接 shell，独立于交互终端）

## 四、项目设计层面观察

1. **OpenMinis 的强项是底座**：权限体系（ConfigConfirmationGate）、沙箱、Agent 循环（历史压缩/迭代上限）、数据层（Room）——全部保留不动
2. **OpenMinis 的弱项是交互打磨**：所有 UI 都是"功能可用"级，没有 v1 那种"手感级"打磨（惯性/拖柄/粘滞视觉反馈）——这正是 v1 资产价值所在
3. **融合原则**：底座用 OpenMinis，交互用 v1 的设计语言，功能用 v1 的完整清单——三层各取所长

## 五、建议执行顺序

```
现在：L1 装机验证（本轮）
下一步：L2 交互对齐（惯性滚动+回底+粘贴=先做，选区拖柄=后做）
并行：L3 的 ⌘ 命令面板（独立可并行）
之后：AI 终端区（依赖 ChatScreen 改造，随战役 C/D）
```
